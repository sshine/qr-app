## name: playwright-tests description: Conventions for this project's Playwright end-to-end suite under e2e/. Use when writing, renaming, debugging or reviewing a test in e2e/, when deciding whether a frontend change needs an e2e test at all, and when driving the playwright-test-planner, playwright-test-generator or playwright-test-healer agents.

# Playwright tests

The suite lives in `e2e/`. Everything comes from the flake: `playwright` is on `PATH` in the
devshell, `@playwright/test` resolves off `NODE_PATH`, and the browsers are in the store. There is
nothing to install.

```
just e2e                      # the whole suite
just e2e -g "log in"          # one test
just e2e --headed --ui        # needs `nix develop .#headed`
playwright show-report e2e/playwright-report
```

## When a change earns a test

Add one when the change carries a property that can be stated as a sentence about behaviour:

- a flow that must complete end to end,
- a rule the interface claims to enforce,
- state that must survive a reload, a new tab, or a discarded session,
- an authorisation boundary.

Do not add one for restyling, copy edits, or markup that no invariant depends on. A test that
asserts the current markup and nothing more will fail on the next redesign and teach nobody
anything.

## Naming

Name a test after the invariant, not the incident.

```
✗ test("regression for #42", ...)
✗ test("password field", ...)
✓ test("holds back a password that breaks the rule the form states", ...)
✓ test("treats an email as one account whatever its case or surrounding space", ...)
```

The name is what a reader sees in the failure report. It should say what stopped being true.

## Structure

- One property per test. If a flow has phases, use `test.step` inside one test rather than splitting
  it into tests that depend on each other's leftovers.

- Tests run in parallel and in any order. Never rely on another test having run.

- Generate fixture data per test rather than sharing it. Where the backend collapses repeats of a
  field onto one row, a reused value means the test exercises a row it did not create:

  ```ts
  function uniqueEmail(): string {
    return `e2e-${Date.now()}-${Math.random().toString(36).slice(2, 8)}@example.test`;
  }
  ```

## Locators

Role and label, never CSS or XPath. `{ exact: true }` where one label is a substring of another:
"Confirm Password" also contains "Password".

```ts
await page.getByLabel("Password", { exact: true }).fill(password);
await page.getByRole("button", { name: "Create account" }).click();
```

For data that varies between runs, a regular expression keeps the locator resilient rather than
loosening it to a CSS selector.

Never wait for `networkidle`, and do not reach for `waitForTimeout` where a web-first assertion will
do. `expect(...).toHave*` retries; a sleep does not.

## When the browser stops being the right level

Client-side validation is the usual case. Once a form refuses to submit, the UI path can no longer
reach the server behaviour, and the browser test degenerates into asserting that nothing happened.
At that point the rule needs a second test at the API level, through the `request` fixture:

```ts
const response = await request.post("/signup", {
  form: { email, password: tooShort, confirm_password: tooShort },
  maxRedirects: 0,
});
expect(response.status()).toBe(303);
expect(response.headers()["location"]).toContain("error=short");
```

A rule enforced only in the browser is not enforced. When a UI test starts passing because the form
blocks submission, that is the signal to add the API test, not to delete the UI one: the pair says
both that the form states the rule and that the server holds it.

## Comments

Comment the assertion whose failure would be misread, and say what the distinct failure modes are:

```ts
// Read the received URL on failure; the two ways this breaks are distinct:
//   /login?error=credentials   no user row matched, or the hash did not verify
//   /login (no query)          credentials were accepted, then the cookie was dropped
await expect(page).toHaveURL("/");
```

Leave the obvious lines bare.

## Red first

Write the failing test before the fix, and read the failure. A test written after the fix proves
only that the code runs. The failure output is the part that tells you the test is pointed at the
right thing.

## Driving the agents

Three agents live in `.claude/agents/`, generated by `playwright init-agents --loop=claude`:

- **planner** explores the running application and writes a plan,
- **generator** turns a plan item into TypeScript, verifying each selector live,
- **healer** replays a failing test and patches it.

Plans go in `e2e/specs/`. Ask for that path explicitly: the generated agent definitions' examples
say a bare `specs/`, so an unqualified request writes to the wrong place.

The generator starts from `e2e/tests/seed.spec.ts`. Leave that file as it is.

Regenerate all three after a Playwright upgrade; the MCP tool list changes between versions:

```
playwright init-agents --loop=claude -c e2e/playwright.config.ts
```

Output the healer leaves behind is worth reading before rerunning: `e2e/test-results/<slug>/ error-context.md` holds the page snapshot at the moment of failure.
